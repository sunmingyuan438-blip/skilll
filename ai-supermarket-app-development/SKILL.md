# AI 超市应用开发

这个 Skill 把重复的新应用开发前置工作固化为一条可复用流程：

`研究 → 产品发现 → 产品简报 → AIGZM 接入决策 → 方案设计 → 开发实施 → 验收复盘`

它适用于“做一个新的 AI 应用”“开发 AI 超市应用”“做一个 AI 工具/Agent/数据应用”“把应用接入 AI 超市”等请求。用户明确调用 `$ai-supermarket-app-development` 时直接使用本 Skill。

## 总体约束

- 默认先研究和澄清，不立即写代码、搭页面或决定技术栈。
- 用户给出想法后优先进入 `RESEARCH`，先查找相似产品、公开案例和开源项目；研究结论必须带来源与日期。
- 只问一个最重要的问题，按回答动态追问；每个主题结束后总结并让用户纠正。
- 持续维护三栏：**事实、假设、未知项**。假设不能伪装成需求。
- 不把“使用 AI”本身当作价值，必须说明用户、场景、问题和可观察结果。
- 不要因为竞品存在就否定想法，也不要因为找到开源仓库就默认可以直接商用；解释差异、许可证、活跃度、集成成本和风险。
- 在用户确认产品结论前不进入方案；在用户确认方案前不进行代码变更。
- 不执行部署、付费、发邮件、发布、申请审核等外部不可逆动作，除非用户在该动作前明确授权。
- 发现关键信息冲突时先停下来指出冲突，只问一个决定性问题。

## 阶段 0：启动和范围判断

先判断请求是否属于“新 AI 应用”。如果只是修 bug、改一个文案、调一个样式或补一个局部接口，不启动完整流程，直接按普通开发工作处理。

属于新应用时，先告知用户：

> 我会先做公开资料和开源项目扫描，再通过一次一个问题的方式确认产品方向；随后读取 AIGZM 官方开发者文档，把接入、计费、安全、Sandbox 和 AI 超市发布要求写进需求。产品和方案确认前不会开始编码。

如果用户说“AI 超市”，先确认它代表哪种产品形态：AI 工具目录、模型聚合平台、应用市场、场景解决方案商店、Agent 市场、企业内部能力中心或其他形式。不要自行假定。

## 阶段 1：RESEARCH 公开资料与开源扫描

收到用户的想法后，提取搜索关键词、可能的产品类别、目标用户和关键技术词。想法足够明确时立即搜索；只有在无法形成有效搜索词时，才先问一个最小澄清问题。

研究至少覆盖：

1. **相似产品和公开案例**：官网、产品文档、定价页、发布公告、用户案例和真实用户讨论。
2. **开源项目**：GitHub、GitLab、Hugging Face 或官方仓库，检查 README、许可证、最近活动、发行版、Issue、部署方式和核心依赖。
3. **AIGZM 官方开发者文档**：每次进入方案或开发前都重新读取官方实时入口，具体要求见 [AIGZM 接入约束](references/aigzm-requirements.md)。

优先使用第一方来源。技术、许可证、模型可用性、数据接口、计费和安全规则必须回到官方文档或官方仓库核实。没有联网能力时，明确说明研究受限，不得假造搜索结果、仓库状态或 API 字段。

输出“外部研究快照”，至少包含：

- 搜索关键词、研究范围、来源和访问日期；
- 相似产品表：目标用户、核心场景、主要能力、可借鉴点、空白或限制；
- 开源项目表：仓库、许可证、最近活动、技术栈、可复用模块、部署/集成难度、商用注意事项；
- AIGZM 文档读取记录和与该想法相关的模型、数据 API、OAuth、Billing、Webhook 或 AI 超市发布要求；
- 来源明确的事实、基于来源的推断、待验证假设；
- 3—5 个最值得后续确认的问题。

研究用于提出更好的问题，不替用户决定产品方向。找不到可靠匹配时明确写出搜索范围和“未找到足够可靠的匹配”，不要硬凑结果。

详细字段和输出格式见 [工作流模板](references/workflow-templates.md)。

## 阶段 2：DISCOVERY 产品发现

研究快照完成后，进入逐题对话。每次只问一个问题，优先询问会改变产品方向的内容，按以下顺序灵活推进：

1. **想法和边界**：一句话定义、入口、核心结果、不属于什么；
2. **第一优先用户**：角色、经验、设备、使用环境、触发时机、不服务的人、使用者/决策者/付费者差异；
3. **问题和任务**：用户要完成的任务、真实触发场景、当前替代、时间/成本/质量/风险、最近一次例子；
4. **价值和结果**：用户完成任务后的可观察结果、切换理由、最小价值行为；
5. **核心流程**：进入 → 输入 → AI/系统处理 → 用户判断/编辑 → 输出/行动 → 反馈；
6. **AI 边界**：AI、规则、数据库、外部工具和人工分别负责什么，低置信度如何处理；
7. **数据与信任**：敏感数据、权限、保存期限、来源、可解释性、滥用和人工接管；
8. **MVP 范围**：`MUST`、`SHOULD`、`LATER`、`OUT`；
9. **约束**：平台、已有仓库、技术栈、时间、预算、团队、登录、计费、权限和多端；
10. **成功标准**：用户价值、产品行为、AI/系统质量、成本或运营指标。

遇到“所有人”“提高效率”“功能越多越好”等宽泛表达，要求用户给出具体用户、场景、动作、结果或例子。遇到功能清单，先翻译为用户问题和期望结果，再判断优先级。

每个主题完成后用 3—6 条要点总结，明确哪些是事实、假设和未知项。信息足够后切换到 `SYNTHESIS`。

## 阶段 3：SYNTHESIS 产品简报和确认闸门

输出一份产品发现简报，至少包含：

- 一句话产品定义：为谁、在什么场景、解决什么问题、通过什么能力、得到什么结果；
- 第一优先用户和暂不服务的人；
- 核心问题、当前替代和问题证据；
- 核心价值链；
- AI、确定性逻辑和人工确认的边界；
- MVP `MUST/SHOULD/LATER/OUT`；
- 成功指标；
- 外部研究和 AIGZM 依赖；
- 风险、待验证假设和仍需确认的决策。

然后暂停并问：

> 以上是产品发现结论。请回复“确认，进入方案设计”，或直接指出需要修改的部分。没有确认前，我不会进入设计或编码。

没有明确确认时，留在 `SYNTHESIS`，只修改简报或补问关键问题。

## 阶段 4：AIGZM 接入决策

在设计之前读取 [AIGZM 接入约束](references/aigzm-requirements.md)，并重新核对官方实时文档。将以下内容写入需求，而不是只放在实现备注里：

- 选择唯一身份模式：Developer API Key、OAuth 登录、OAuth + `points.spend` 或 OAuth + `billing.initiate`；
- 文档真源顺序：`openapi.json`、实时模型文档、实时数据 API 文档、安全接入指南、官方示例；
- 实时 `model_key`、数据 endpoint、调用入口、参数、积分、超时和幂等键策略；
- 会员信息和钱包读取：`/v1/user/membership`、`/v1/user/membership/details`、`/v1/user/wallet`，以及禁止缓存、只能读取当前授权用户的限制；
- 充值和会员购买：`POST /v1/user/billing-entries`、`GET /v1/user/billing-entries/{entry_id}`，回跳后仍必须查询 `payment_order.status=paid`；
- AI 超市一次性购买：商业报价、公开详情和 `/v1/user/app-entitlement` 权益判断，Token 消耗单独计费；
- API Key 激活、服务端密钥保存、鉴权头二选一、错误映射和余额不足处理；
- OAuth PKCE、`state`、`nonce`、issuer/audience、`issuer + sub` 身份键和 Scope 最小化；
- Sandbox 与生产隔离、OAuth 回调白名单、支付回跳白名单、Webhook 验签和 `event_id` 去重；
- `billing_url` 只做浏览器跳转，支付成功以查询到 `payment_order.status=paid` 为准；
- 数据 API 的动态目录、原样透传、`X-IdP-*` 计费/错误响应头和上游失败处理；
- 应用托管：开通申请、套餐、`static_site`/`nodejs`/`python` 模板、zip 上传、构建、健康检查、回滚、空闲挂起和第三方出站网络放行；
- 数据库：托管实例的 MySQL、容器内 `DATABASE_URL`、本机 `sql-query` 管理接口、查询超时/行数限制和迁移/seed 顺序；
- 托管包和运行约束：20 MB zip、根目录入口、`PORT=8080`、只读文件系统、60 秒健康检查、10 秒 `SIGTERM` 和环境变量重新部署；
- 托管环境变量导入：`AIGZM_CLIENT_ID`、`AIGZM_CLIENT_SECRET`、`AIGZM_REDIRECT_URI`、`AIGZM_BILLING_RETURN_URI`、`AIGZM_WEBHOOK_URL`、`AIGZM_WEBHOOK_SECRET`、`AIGZM_API_KEY`、`AIGZM_EXPECTED_ISSUER`，并记录 Secret/Key 轮换影响；
- 不拉取、搜索、导出或关联全量会员、其他应用用户或跨应用身份；
- API Key、Client Secret、Access Token、授权码和敏感输入不进入前端、URL、源码或日志；
- 需要 AI 超市发布时，核对 Sandbox 基础接入、正式申请、`homepage_url`、应用状态、Scope、回调、Webhook 和审核影响。

如果应用不需要 AIGZM 模型、数据、OAuth、Billing 或 AI 超市发布，明确记录“不接入的原因”，不要假装已经完成接入设计。

## 阶段 5：DESIGN 方案设计

只有用户确认产品简报后才进入 `DESIGN`。先检查当前仓库、文档、依赖、运行方式和现有约定，再提出 2—3 个可行方案，说明适用条件、成本、风险和扩展性，并给出推荐方案。

设计至少覆盖：

- 端到端用户流程、页面/入口和核心状态；
- 组件边界、数据流、持久化和权限；
- AI 调用链、模型选择、工具/知识来源、提示词和人工接管；
- AIGZM 请求/响应、计费、超时、幂等、错误、重试和动态索引；
- OAuth、API Key、Sandbox、生产和 Webhook 的安全边界；
- 数据隐私、敏感日志、许可证和第三方依赖；
- MVP 验收标准、测试策略、上线检查和明确不做的内容。

设计完成后暂停并问：

> 以上方案是否确认？请回复“确认，开始开发”或指出需要调整的部分。

## 阶段 6：BUILD 开发实施

只有用户明确确认方案后才开始开发。先给出分步骤计划、涉及文件和每一步的验收方式；必要时先写实施计划，再改代码。

执行时：

- 遵循现有项目结构，避免无关重构；
- 先实现一条可运行的核心价值闭环；
- AIGZM 请求严格依据官方 OpenAPI 和实时模型/数据 API 文档，不猜路径、不保存静态模型或接口白名单；
- 只使用一种匹配的身份模式，凭据仅服务端保存；
- 实现合适的超时、幂等键、错误映射、余额不足、上游故障、空结果和低置信度处理；
- 会员、钱包、应用购买权益和支付状态以后端查询结果为准；Webhook 先验签、去重，再更新本地状态；
- 托管部署包遵循对应模板的构建规则；数据库只使用 `DATABASE_URL` 或官方 SQL 管理接口，不把 SQLite、日志或上传文件写到持久本地磁盘；
- 对托管实例唤醒期间的 `503`、`Retry-After` 和 `X-Idp-Wake-Page` 只重试幂等请求；
- 保护用户数据，日志和错误上报做敏感字段脱敏；
- 复用开源项目时记录仓库、版本、许可证、修改范围和履行义务；
- Sandbox 和生产配置、数据、Webhook、凭据与日志隔离；
- 对支付、上线申请或外部发布动作停在准备阶段，等用户明确授权后再执行。

每完成一段工作，报告修改内容、原因、验证命令、结果和剩余风险。不得在没有验证时声称完成。

## 阶段 7：REVIEW 验收复盘

开发后输出：

- 已实现的 MVP 能力及其对应的用户问题；
- 产品简报、AIGZM 接入决策和实际实现的差异；
- 单元/集成/构建/手工验收证据；
- Sandbox 或正式联调证据（如适用）；
- API、Webhook、计费、错误、超时和敏感数据检查结果；
- 会员、钱包、应用权益、充值/会员购买和一次性应用购买检查结果；
- 托管部署、回滚、环境变量、健康检查、空闲唤醒和 MySQL `DATABASE_URL` / SQL 管理检查结果；
- 已知限制、许可证义务、未完成事项和下一步建议。

至少核对 OpenAPI 契约、AIGZM Sandbox 成功/失败路径、幂等重试、余额不足、上游失败、Webhook 验签去重和敏感信息泄露风险。

## 可用指令

- `开始探索`：从当前想法重新开始；
- `重新研究`：重新搜索相似产品、公开案例和开源项目；
- `只看开源`：只扫描可复用仓库并检查许可证与部署条件；
- `只看相似产品`：只扫描竞品、替代方案和用户反馈；
- `重新读取 AIGZM 文档`：刷新官方开发者文档、实时模型和数据 API 索引；
- `检查托管要求`：检查当前应用的模板、zip、环境变量、数据库、健康检查和部署约束；
- `总结当前结论`：展示事实、假设和未知项；
- `缩小 MVP`：重做 MUST/SHOULD/LATER/OUT；
- `比较方案`：输出 2—3 个产品或技术方案；
- `生成产品简报`：信息足够时输出 SYNTHESIS；
- `进入方案设计`：仅在产品简报已确认后进入 DESIGN；
- `开始开发`：仅在方案已确认后进入 BUILD；
- `回到研究`：退回 RESEARCH；
- `暂停`：保留当前资料和结论，不继续推进。

根据当前阶段逐步产出，不要一次生成无关的大文档：

3. AIGZM 接入决策；

5. 开发实施计划；
